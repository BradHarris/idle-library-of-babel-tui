## Context

The game has 7 worker tiers in `config.js`: Writer → Manager → Overseer → Rector → Cardinal → Pope → Archbishop. Each tier has a `baseCost` and an `autoHireBelow` field.

The current `tick()` function in `src/game.js` has two separate systems:
1. **Pages/money calculation**: calls `calcPagesPerSecond()` which sums ALL workers (bug — should only count writers)
2. **Auto-hire timer**: every 30s, for each non-writer tier, spends money to hire one worker of the `autoHireBelow` tier

Neither system implements the intended cascade model.

## Goals / Non-Goals

**Goals:**
- Implement per-tick cascade: each tier adds the count of the tier above it to its own count
- Fix `calcPagesPerSecond` to return only writer count
- Remove the auto-hire timer system and related state
- Remove `autoHireBelow` from tier configs
- Clean up unused code

**Non-Goals:**
- Adding new tiers or mechanics
- Changing save/load format (no save system exists yet)
- Performance optimizations
- Refactoring the UI or rendering

## Decisions

### Decision: Cascade order — top-to-bottom (rector first, writer last)

**Rationale:** We must cascade from the top tier down so that a newly spawned overseer can itself spawn a manager in the same tick, and so on. This produces the full cascade chain in a single tick.

```
rectors → overseers → managers → writers → pages
```

If we went bottom-to-top, managers would spawn from overseers but those new managers wouldn't spawn writers until the next tick. Top-to-bottom gives the full cascade each tick.

### Decision: Use old counts for page generation

**Rationale:** The page generation should use the writer count from the start of the tick (snapshot), not the post-cascade count. This prevents double-counting: pages are generated by the writers that existed during the tick, not by writers spawned mid-tick.

### Decision: Remove `autoHireBelow` from tier configs entirely

**Rationale:** The field only served the auto-hire system. Since that system is being replaced, the field has no purpose. The tier config becomes simpler — just `id`, `name`, and `baseCost`.

### Decision: Remove `_autoHireTimers` from game state

**Rationale:** These timers are only used by the auto-hire system. With the cascade replacing auto-hire, there are no timers to manage. This simplifies the state object.

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| Players progress much faster (free cascade vs money-cost timer) | This is the intended design. If too fast, base costs or tick intervals can be tuned later. |
| Exponential growth: with 7 tiers, a single rector → 1 overseer → 1 manager → 1 writer → 1 page per tick (chained), but with multiple higher-tier workers the lower tiers grow exponentially | This is correct idle-game behavior. Exponential growth is expected. |
| Breaking existing saves (if save/load is added later) | No save system exists currently, so no breakage. |

## Migration Plan

N/A — no save system exists. When one is added, the cascade model should be the default.

## Open Questions

1. Should the cascade use the old writer count or the new (post-cascade) writer count for page generation? Current design uses old count (conservative, prevents double-counting).
2. Should `baseCost` still exist if workers are now free via cascade? The cost is still relevant for manual purchases (`purchaseWorker`), so it stays.
